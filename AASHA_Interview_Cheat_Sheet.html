1. What problem does AASHA solve?

The Context & Constraints

  • Rural Connectivity Constraints: ASHA workers operate in remote villages where internet connection is spotty, slow, or completely absent.
  • Data Collection Delays: Traditional systems crash or freeze without internet, forcing workers back to paper logs and delaying reporting to health centres.

The AASHA Solution

  • Offline-first
    Meaning: The app works even when there is no internet.
    In AASHA: Allows health workers to log visits, process languages, and evaluate patient risk with zero connection.

2. What is the basic idea?

1. Input Text/Voice → 2. Local Regex/NLP Parse → 3. Save to IndexedDB → 4. Local Risk Flag → 5. Auto-Sync on Internet

Write-First, Sync-Later

ASHA workers capture observations directly on-device. The application extracts symptoms and immediately sets the patient risk level offline. When an internet connection becomes available, the client automatically sends the saved health records to the server.

No Diagnosis — Risk Flagging Only

  • Risk flagging
    Meaning: Checking health information against rules to identify potentially risky cases.
    In AASHA: We parse observation logs to count fever days, detect high blood pressure, and flag critical patients without making a medical diagnosis.

3. What are the main components and what does each do?

Frontend (PWA Client) Implemented

  • PWA
    Meaning: A web app that works like a mobile app and runs offline.
    In AASHA: Holds the UI, local IndexedDB storage, and client-side regex parsing engines.

Backend (Spring Boot) Implemented

  • Spring Boot
    Meaning: The framework we use to build the backend.
    In AASHA: Handles HTTP requests, runs the server-side risk engine, and coordinates database writes.

AI Service (Bedrock Client) Implemented

Sends records to AWS Bedrock to extract symptoms and get an explainable risk rationale when data is synchronized to the server.

Voice Speech-to-Text Implemented

Uses browser's native webkitSpeechRecognition to listen to voice notes and convert speech to text on the worker's device.

External Python AI Service Unverified Resume Claim

The README claims a separate Python NLP + Risk Engine service exists. Methodology not verified: No such directory exists; Spring Boot interacts with Bedrock directly.

4. How does an ASHA worker create a record?

1. Inputs Metadata & Narrative

The worker enters basic patient data (Name, Age, Phone, Patient Type) and dictates or types the case narrative (e.g. "pregnant patient has foot swelling and high blood pressure").

2. Immediate Local Assessment

The local Javascript parser extracts symptoms (e.g. "swelling" and "high bp"). It runs the local rule engine to flag the patient as "High" risk, saving it instantly to the offline database.

5. What happens when there is NO internet?

Local Storage & Draft Auto-Save

  • IndexedDB
    Meaning: A browser database used to store data locally.
    In AASHA: We use it to save patient records with a pending status when offline.
  • Auto-Save Drafts: Form values are saved to IndexedDB on every keypress so data isn't lost if the browser tab closes.

Offline Soft-Deletes

When a worker deletes a patient record offline, the app marks the record's status as pending-delete instead of removing it. The record is deleted from the server when connectivity returns.

6. What happens when internet comes back?

Online Reachability Check

The app regularly checks network reachability by fetching a small response from Google's servers and the backend server. It triggers sync only when true internet reachability is confirmed.

Synchronization & Resolving Conflicts (LWW)

  • Synchronization
    Meaning: Sending locally saved records to the server when internet returns.
    In AASHA: The client pushes all pending offline updates in a batch to the backend.
  • Last-Write-Wins (LWW): The server compares timestamps. It ignores the incoming sync record if the database has a newer or identical updatedAt timestamp.

7. How does the frontend communicate with the Spring Boot backend?

API Calls & Batch Payloads

  • REST API
    Meaning: A way for the frontend and backend to communicate.
    In AASHA: The client posts JSON payloads to /api/sync (for batch uploads) and sends DELETE calls to /api/records/{id}.

Communication Sequence

Client → POST /api/sync (Batch JSON) → Server → Responds {synced: N, duplicates: M} → Client marks 'synced'

8. How is the data stored in PostgreSQL?

Relational Storage & Schema

  • PostgreSQL
    Meaning: The database where the server stores health records.
    In AASHA: Persists metadata, timestamps, and patient categories in a structured table called health_records.
  • JPA/Hibernate
    Meaning: Tools that connect Java objects with database tables.
    In AASHA: Maps the Java HealthRecord entity class to our PostgreSQL database tables.

JSONB for Dynamic Symptoms

Symptoms vary wildly by patient. The backend stores dynamic symptom details inside a PostgreSQL jsonb column named structured_json, mapped to a Java Map object.

9. How does risk flagging work?

Rule-Based Decision Logic

Rules run locally in JavaScript and server-side in Java:

  • Pregnant: Bleeding → Critical; High BP + Swelling → High; Fever ≥ 4 days → Medium.
  • Child / Adult / Elder: Breathing Issue → High. Fever ≥ Elder (3 days), Child (4 days), Adult (5 days) → Medium.

Backend AI Triage

When online, the Spring Boot app calls AWS Bedrock to extract symptom tags and generate a human-readable reason (e.g. "high risk due to breathing trouble and advanced age") for PHC dashboards.

10. What exactly did we test with k6?

  • k6
    Meaning: A tool that simulates users to test how much load the backend can handle.
    In AASHA: We ran load and stress tests against the backend endpoints to verify server scalability under heavy concurrent sync operations.

Simulated Scenarios

Simulated 10 to 500 Virtual Users (VUs) writing and fetching records. Throughput peaked at 522 requests/sec. Under mixed load (70% GET, 20% POST, 10% Sync), P95 latencies remained stable under 500ms at 100 VUs.

Interview Rapid Fire

  • Q: Why use IndexedDB over LocalStorage?
    A: LocalStorage is limited to 5MB and blocks the main UI thread. IndexedDB is asynchronous and handles hundreds of megabytes of structured JSON data without freezing the screen.
  • Q: How do you handle sync conflicts?
    A: We use Last-Write-Wins (LWW). The client includes an updatedAt timestamp. The server drops incoming sync payloads if its current database record is newer.
  • Q: What is the benefit of Spring Boot Virtual Threads?
    A: We enable them via spring.threads.virtual.enabled=true in Java 21. They let the backend handle thousands of concurrent synchronization requests using lightweight threads instead of blocking database connection pools.
  • Q: How does the client verify true internet?
    A: It checks browser status first, then sends active HTTP GET calls to a Google test page and the backend /healthz endpoint to verify true server reachability.
